# 拾海 PickOcean｜海大黑客松作品

> 從 AI 輔助開發，到思考如何真正解決問題

「拾海 PickOcean」是一個以地圖為核心的海洋廢棄物回報與淨灘活動平台。我們希望把分散的海廢通報和淨灘資訊放在同一個地方，讓民眾更容易了解海岸垃圾分布，也更容易找到可以參與的清理活動。

**參賽成果：** 海大黑客松技術組佳作  
**專案性質：** 黑客松作品與學習用 MVP  
**主要技術：** HTML、CSS、JavaScript、Leaflet、Node.js、Express、MongoDB、Mongoose

## 參賽動機與主題發想

參加國立臺灣海洋大學黑客松，是希望在新手友善的活動中學習如何運用 AI 協作開發網頁，並在有限時間內完成一個有實際應用方向的作品。參賽前，我先了解過去黑客松作品和常見題目，思考如何用地圖呈現環境問題的位置，以及不同時間的回報分布。

我們注意到，海洋廢棄物通報和淨灘活動資訊分散在政府、民間平台與不同社群中。因此，團隊將題目聚焦在海洋廢棄物，希望整合海廢回報、地圖標記、淨灘活動發布與報名，降低民眾參與環境保護的門檻。

## 作品功能

- 在互動地圖查看垃圾回報、一般活動和淨灘活動，並依類別篩選。
- 使用 GPS 或在地圖上點選位置新增標記；含 GPS 資訊的 JPEG 照片可協助帶入位置。
- 回報垃圾類別、數量、嚴重程度和照片；特殊危險項目會顯示風險提醒與通報資訊。
- 透過清理確認和自動整理追蹤垃圾點位狀態。
- 發布淨灘活動、報名或取消報名、留言並查看活動資訊。
- 查看天氣、歷史時間範圍和公開個人資料；地圖標記會依縮放程度聚合。
- 網路中斷或送出失敗時，回報可暫存在瀏覽器，網路恢復後再嘗試同步。

## 團隊分工與開發過程

團隊由兩人組成。我主要負責初期主題發想、專案方向規劃，以及網頁端的開發與測試；隊友主要負責專案分析、實際通報問題的資料蒐集，以及企劃書、市場規模與營運模式整理。

我當時還不熟悉完整的前後端開發流程，因此把生成式 AI 作為主要輔助工具。開發時，我先提出想解決的問題和希望完成的功能，再和 AI 討論技術方向與可行性；接著由我評估方案是否適合專案，選擇實作方向、測試功能，並根據結果繼續修正。

網站以前端 HTML、CSS 和 JavaScript 呈現介面與處理操作，透過 Leaflet 建立互動地圖；後端使用 Node.js 和 Express 提供 API，並以 MongoDB 儲存回報和活動資料。除了撰寫程式，我也需要思考前後端如何交換資料、資料要如何保存，以及使用者完成操作後應該看到什麼結果。

黑客松的時間壓力比我預期更大。當時使用的 Codex 免費方案有使用額度限制，額度隨開發逐漸消耗，而展示期限也愈來愈近。遇到功能錯誤時，我會擔心剩下的時間和額度是否足夠排除問題。經過持續討論、修改與測試，團隊最後仍讓主要功能成功運作並完成展示。

## 技術學習：用白話認識網頁建置

| 詞彙 | 白話解釋 | 在拾海中的用途 |
| --- | --- | --- |
| 前端（Frontend） | 使用者看得到、按得到的網站部分 | `index.html`、`styles.css`、`script.js` 建立畫面、表單和互動。 |
| 後端（Backend） | 在伺服器運作、接收請求並處理資料的部分 | `server.js` 啟動伺服器；`app.js` 處理 API 和資料。 |
| API | 前端和後端交換資料時使用的入口與規則 | 例如 `GET /api/markers` 讀取標記，`POST /api/markers` 新增標記。 |
| HTTP 方法 | 表示要對資料做什麼的動作 | `GET` 讀取、`POST` 新增、`PUT` 更新、`DELETE` 刪除。 |
| 資料庫（MongoDB） | 可以長期保存網站資料的地方 | 保存地圖回報、活動、留言和個人公開資料。 |
| 資料模型（Schema） | 說明一筆資料有哪些欄位、長什麼樣子的規格 | `models/` 和 `SCHEMA.md` 描述標記與使用者資料。 |
| Leaflet | 用來建立互動地圖的 JavaScript 套件 | 顯示地圖、位置標記、縮放和定位功能。 |
| Node.js／Express | 在伺服器執行 JavaScript／建立網站服務的工具 | 接收瀏覽器請求，提供網頁與 API。 |
| 套件／依賴 | 專案使用的現成程式工具 | `package.json` 記錄 Express、Mongoose、Multer 等套件。 |
| `.env` 環境設定 | 放置程式設定值的檔案 | 可設定資料庫連線或天氣服務金鑰；真正的 `.env` 不應公開。 |
| localStorage | 瀏覽器裡保存少量資料的空間 | 目前記住免登入裝置識別；清除瀏覽器資料後識別會改變。 |
| IndexedDB | 瀏覽器內較適合保存較多資料的本機資料庫 | 暫存未成功送出的回報，之後再嘗試同步。 |
| REST API | 用固定網址和 HTTP 方法操作資料的一種常見 API 設計方式 | 讓前端用讀取、新增、修改等請求和後端交換資料。 |
| GPS／EXIF | GPS 是定位資訊；EXIF 是照片可能附帶的拍攝資訊 | 可協助從照片讀出拍攝座標，也可能意外揭露位置隱私。 |
| MIME type | 檔案宣稱自己的格式標籤 | 上傳功能用它初步確認檔案類型，但不能單靠它保證檔案安全。 |
| XSS／HTML 跳脫 | 把惡意文字當網頁程式執行的漏洞／將特殊符號安全地顯示成文字 | 前端使用 `escapeHtml` 處理部分使用者內容，降低文字被當成 HTML 執行的風險。 |
| MVP | 先完成核心用途、可以操作展示的初版 | 拾海已能展示主要概念，但正式帳號、安全和部署等還可繼續完善。 |

## 參賽後的反思：完成作品不等於真正理解技術

參賽前，我以為黑客松最重要的是在有限時間內做出功能。AI 確實幫助我跨過許多技術門檻，讓我能在還不熟悉完整網頁流程時，把前端、後端和資料庫串接起來。但作品能運作之後，我也開始問自己：如果沒有 AI 即時提供程式碼和解法，我是否能獨立完成或排除問題？

我能提出功能需求、和 AI 討論方案、做出選擇並測試結果，但這不代表我已經完全理解每段程式背後的原理。遇到複雜問題時，我有時仍依賴 AI 指引下一步，而沒有先從問題本身開始分析。這次經驗也讓我重新看待過去的演算法練習：理解題目、運用方法解題，和把技術用在真實專案中，是不同層次的能力。

我也發現，黑客松不只是在比賽期間比開發速度。許多參賽者已透過過去的專案，累積技術選擇、議題分析和作品規劃經驗。相較之下，我當時太專注於快速做出功能，忽略了賽前累積技術和問題分析能力的重要性。

## 未來可以補充的功能與架構

### 先補強可靠度與安全性

1. **正式登入與帳號驗證：** 目前以瀏覽器 `localStorage` 的 `userKey` 辨認使用者，並非真正登入。未來可加入可靠的帳號驗證與跨裝置同步。
2. **伺服器端權限判斷：** 編輯、刪除、報名等操作應由伺服器根據已驗證的登入狀態確認權限，不應只相信瀏覽器送來的 `userKey`。
3. **輸入驗證與濫用防護：** 統一檢查欄位格式、內容長度和請求頻率，加入 API rate limit、檢舉和管理員審核。
4. **正式部署與資料保存：** 啟用 HTTPS 和安全標頭，為資料庫建立備份；把圖片移至有適當權限管理的雲端儲存，並規劃容量與保存期限。
5. **測試與錯誤監控：** 為主要操作和 API 增加測試與錯誤紀錄，確保資料庫或天氣服務暫時失效時能提供清楚提示。

### 再逐步擴充使用體驗

- 增加手機版、無障礙操作，以及不依賴地圖的清單瀏覽方式。
- 增加地點、日期和狀態搜尋，並改善大量標記時的載入速度。
- 加入資料審核、管理員角色、檢舉與使用者封鎖流程。
- 明確說明定位、照片和個人資料的用途、公開範圍與保存期限。
- 隨功能增加整理前端、後端和資料模型的資料夾結構，並考慮自動化部署。

## 密碼、資安與隱私注意事項

- **目前沒有正式密碼登入。** `userKey` 是瀏覽器中的裝置識別，不是密碼，也不能視為安全帳號。使用者可修改送到 API 的值，所以目前的免登入識別不適合作為正式權限保護。
- **機密不要放進前端或 Git。** 不要公開密碼、資料庫連線字串或 API 金鑰。`.env` 雖列在 `.gitignore`，仍要檢查機密是否曾經被提交；若外洩，應立即撤銷或更換。
- **localStorage 不是保險箱。** 網頁程式可能讀取其中資料，因此不要存密碼或長期有效的登入憑證。
- **上傳檔案需要多層檢查。** 副檔名和 MIME type 可能不可信；正式服務應驗證檔案內容、限制格式與大小，並避免儲存空間被耗盡。照片也可能帶有 EXIF GPS 位置。
- **定位和個人資料可能被公開。** 回報座標、信箱、暱稱與個人介紹可能讓人推知身分、住處或行程；分享前應確認自己願意公開。
- **輸入要驗證，顯示也要安全處理。** `escapeHtml` 是有幫助的前端防護，但不能取代後端驗證、權限檢查及對外部網址的安全檢查。
- **正式網站需要 HTTPS 和維護。** 本機 `localhost` 適合開發；公開部署還需要 HTTPS、安全設定、依賴更新和資料備份。
- **資料庫與 API 要限制存取。** 不要讓資料庫直接暴露在公網；使用最小必要權限、強密碼與備份，並加入 API 頻率限制以降低濫用。

## 本機啟動

1. 安裝 Node.js 與 MongoDB。
2. 在專案目錄執行：

   ```bash
   npm install
   ```

3. 將 `.env.example` 複製為 `.env`，設定可用的 `MONGODB_URI`。啟用天氣功能時再設定 `OPENWEATHER_API_KEY`。
4. 啟動伺服器：

   ```bash
   npm start
   ```

5. 瀏覽 `http://localhost:3000`。

## 專案檔案

- `index.html`：網頁結構。
- `styles.css`：版面與視覺樣式。
- `script.js`：瀏覽器端互動與地圖功能。
- `server.js`、`app.js`：伺服器啟動和 API。
- `models/`：MongoDB 資料模型。
- `SCHEMA.md`：資料欄位與 API 說明。
- `.env.example`：環境設定範例，不應放入真正機密。

## 專案限制

目前版本是學習用 MVP，尚未完成正式登入、跨裝置帳號同步、API 頻率限制、HTTPS 部署、自動化測試和管理員審核。圖片存放於本機 `public/uploads`，正式上線前應改用具備權限管理、備份和容量規劃的儲存服務。天氣功能需要 OpenWeatherMap 金鑰，可能受服務可用性和額度影響。

## 未來學習方向

這次參賽沒有讓我否定 AI 的價值。AI 能降低學習門檻、協助快速嘗試想法；我希望未來不只把它當成產生程式碼的工具，而能理解它提出的解法。

之後做專案時，我會先分析問題原因、預期結果和可能方向，再尋求 AI 協助；閱讀生成的程式碼，理解資料如何傳遞、函式如何運作，以及系統之間如何連結；並增加實際專案經驗，把程式邏輯用來處理真實需求。AI 可以縮短實作過程，但要讓專案真正解決問題，仍需要開發者理解議題、判斷技術選擇，並能分析和修正問題。

本作品使用生成式 AI 輔助開發。參賽成果為技術組佳作；作品中的功能與技術限制，應以目前程式碼和實際部署狀況為準。
